# Questions readers ask

This collection consolidates the questions readers most commonly ask about the chain-of-custody spec. Each entry carries audience icons so a reader can scan to the questions that matter for their role; the underlying answers cite specific spec sections so claims are verifiable against the source.

## Who each icon means

- 🔍 &nbsp;**Examiner** — FFIEC IT examiners (FDIC, OCC, Federal Reserve), state banking commissioners, NCUA, SEC, NYDFS, state-DOI examiners
- 📋 &nbsp;**External auditor** — financial-statement and SOC engagement auditors
- 🛡 &nbsp;**Internal audit** — institution-side audit function (CAE, internal audit team)
- 📐 &nbsp;**MRM officer** — model risk management lead and model risk managers
- 🏛 &nbsp;**Audit committee** — board-level audit committee and risk-committee readers
- 🛠 &nbsp;**Implementer** — engineers and operators adopting the spec
- ⚖ &nbsp;**Legal counsel** — bank GC, insurer GC, defense civil, plaintiff class-action, e-discovery counsel, admin-law scholar, expert witness
- 🔐 &nbsp;**Privacy counsel** — DPO, GDPR / CCPA / HIPAA / PIPA / DPDP privacy counsel
- 👤 &nbsp;**Data subject** — consumer, end-user, customer (across regimes — "consumer" in US financial regulation, "data subject" in GDPR)
- 📚 &nbsp;**Academic / standards** — IETF/IRTF CFRG reviewer, NIST cryptographer, academic researcher
- ⭐ &nbsp;**Featured** — load-bearing answers worth surfacing first; a reader new to the spec gets the most leverage from the ⭐-tagged questions in any given theme.

Most questions carry two or more icons because most readers share the same concerns. The ⭐ icon is the highlighting axis: filter by ⭐ to find the questions every reader hits first.

## How to filter and sort

- **Sort any column** — click the column header (`⭐`, `Audience`, `Question`, `Answer`, `Spec`). The active column shows ▲ (ascending) or ▼ (descending); click again to reverse.
- **Surface the ⭐ rows first** — click the ⭐ header. Featured questions rise to the top of each theme.
- **Filter to your role** — use the role-filter toolbar at the top of the page (visible in the rendered web view). Each audience icon (`⚖`, `🔐`, `🔍`, `🛠`, `📐`, `🏛`, `📋`, `🛡`, `👤`, `📚`) is a toggle button — click to highlight every row in every theme that carries that audience, click again to clear. The `⭐` button sits left of a thin divider so the "load-bearing" filter axis stays distinct from the audience-affinity axis. Multiple buttons combine with **OR** logic — pressing `⚖` and `🔐` together surfaces every row that matters to legal *or* privacy counsel. The toolbar is sticky so it stays reachable through long scrolls; **Clear all** resets every toggle. Readers viewing the raw markdown can still fall back to browser in-page find (Ctrl+F / ⌘+F) with the icon glyph as the search term.
- **Jump by theme** — the table of contents (left rail in the rendered view) lists every theme heading. Each theme is independent; sorting one doesn't affect the others.

## Tamper detection and independent verification

| ⭐ | Audience | Question | Answer | Spec |
|---|---|---|---|---|
| ⭐ | 🔍 📋 🛡 🏛 | Can the institution alter history without detection? | No. The HMAC chain catches in-flight tampering at re-verification on ingest. The daily Merkle seal under HSM signature catches retroactive tampering. Two independent custody layers must both fail for a successful undetected alteration. | §4.1, §4.2, §4.3 |
| ⭐ | 🔍 📋 🛡 | Can the vendor alter history without detection? | No. The HSM is bank-operated, or per-tenant-segregated when vendor-operated. The signing key is held by the institution and the regulator, not the vendor. The vendor cannot rewrite a sealed root without that key. | §10.5, §10.6 |
| ⭐ | 🔍 📋 | How do we verify the chain independently of the institution's tooling? | The reference verifier is a single static binary with no network calls. It reads the ledger and the public key only. The institution exports the artifacts; the examiner runs the verifier locally. Exit-code semantics make pass/fail unambiguous. | §7, §10.12 |
|   | 📋 🛡 🛠 | What if the verifier itself has a bug? | The reference verifier ships with a published cryptographic conformance corpus (positive and negative test vectors under `spec/test-vectors/`) and is open source. A wary institution runs the conformance corpus against the binary before relying on it. The verifier is replaceable — any conformant implementation produces identical output for the same input. | §7, `spec/test-vectors/` |
|   | 📋 🛡 | How do we test sampling for chain integrity? | Sample-based confirmation walks the chain at randomly-selected event indices: pick an event, verify its per-event MAC against the prior-event-hash chain, then verify the daily Merkle root signature for the day that event was sealed on. Sample size depends on the population; `docs/audit-procedures.md` names a sampling methodology consistent with AS 2315. | §4.1, §4.2, `audit-procedures.md` |
| ⭐ | 🔍 📋 | What stops the institution from rewriting `received_at` on the ledger after capture? | A ledger that mutates `received_at` after ingest is a control failure independent of the chain's cryptographic integrity; SOC engagements test the storage-integrity sample. The chain itself does not depend on `received_at` for integrity — it is forensic metadata only. | §4.2.2 trust posture; `audit-procedures.md` |
|   | 🔍 📋 | What stops a national bank from running a vendor-flag chain and presenting it under FFIEC posture? | §4.1.2 binary conformance — the verifier reads the header HKDF inputs and rejects when they do not match running v1 inputs. There is no silent mode in which a non-FFIEC chain passes FFIEC verification. | §4.1.2, §7 step 2 |
|   | 🔍 📋 | Does the spec resist algorithm-confusion attacks (JWT `alg=none`-style)? | Yes. §4.3 binds the algorithm into `sign_payload` as line 2. §4.3.2 dual-algorithm Variant B forces each algorithm in `signatures[]` to be computed over its own algorithm-named payload, rejecting a shared payload as non-conformant. §7 step 11 rejects algorithm/key-type mismatch with a named reason. | §4.3, §4.3.2, §7 step 11 |
|   | 🛡 🛠 ⚖ | Can opposing counsel attack the chain as a whole? | The chain is three independent layers (per-event MAC, daily Merkle, HSM signature) plus the §7 verifier procedure. Defeating the chain requires defeating all three layers — cryptographically infeasible under §10 threat model. The §7 verifier is the affirmative answer to manipulation claims. | §1.1, §1.4, §7 |
|   | 📚 🛠 | Is the integrity claim falsifiable in the Popperian sense? | Yes. Produce a tampered chain that the §7 procedure does not reject, and the claim is broken. §1.1 Daubert grounding states this explicitly. | §1.1 Testability |

## Custody, keys, and HSM operations

| ⭐ | Audience | Question | Answer | Spec |
|---|---|---|---|---|
| ⭐ | 🔍 📋 🛠 | How is the master HMAC key custody bounded? | The IKM lives in tenant-controlled HSM/KMS custody and never reaches the application host as plaintext. Two delivery models — IKM-delivered to the host under tight handling, and session-key-delivered with HKDF inside the device. 32-byte minimum is normative (RFC 4868); the software-key adapter is excluded from production builds at compile-time and packaging-time. | §4.1.1, §10.6, §10.7, §10.9 |
|   | 🔍 🛠 | What happens if the HSM is unavailable? | The daily seal is delayed. Captured events continue to chain — the per-event HMAC is independent of the HSM. The institution must document the seal delay and re-attempt; sustained delay without explanation is a finding. | §10.16 |
|   | 🛠 📋 | How do we handle key rotation? | IKM rotation crosses the seal boundary: events captured before rotation are signed under the old key; events captured after are signed under the new key. The verifier reads both keys and the rotation event, validates no ambiguous-custody window, and treats unauthorized rotation as a finding. | §10.10, §4.1.3 |
|   | 🏛 🛡 | What's our exposure if the chain has a cryptographic bug? | The chain's substance is well-studied primitives (HMAC, SHA-256, Merkle trees, HSM signatures). Bugs in implementations are publicly catalogued and patched. The conformance corpus ships with positive and negative vectors an institution runs against any verifier build before relying on it. A bug discovered post-deployment triggers an amendment and re-verification. | §7, `spec/test-vectors/` |
|   | 🛠 🔐 | What is the security model for the 16-byte `key_fingerprint` truncation under multi-target collision search? | §10.6's analysis is single-target. Multi-tenant SaaS with N tenants degrades to ≈`128 − log2(N)` effective bits in standard multi-target reductions. §1.3 multi-target security considerations names the degradation explicitly; per-institution IKM isolation (already required) plus a 120-bit floor at the tenant population are the operational guardrails. | §10.6, §1.3 multi-target |
|   | 🛠 📚 | Is the Ed25519 signature deterministic per RFC 8032, or does the spec admit randomised Ed25519? | The verifier-side requires strict canonicalization per RFC 8032 §8.4. The signer-side (HSM) defaults to deterministic Ed25519 (RFC 8032 §5.1.6); institutions whose HSM operates randomised Ed25519 document the DFA-residual posture in CC8.1 per §10.5. | §4.3, §10.5 |
|   | 🛠 📋 | How do I add a new HSM device class (e.g., YubiHSM2, AWS Nitro Enclaves, nCipher nShield 5c)? | §10.5 names FIPS 140-2 Level 3 (or higher) validation with non-extractable Ed25519 (or §4.3.2 dispatched algorithm) signing key and Model A/B handshake support per §4.1.1. New device classes meeting these criteria are conformant; the institution's CC8.1 names the CMVP validation number. | §10.5, §4.1.1 |
|   | 🛠 📋 | What is the cross-cloud key-migration procedure (AWS CloudHSM → Azure Managed HSM)? | Non-extractable Ed25519 means a new key per cloud — a §4.3.2 algorithm-level rotation across `public_key_id` with a documented overlap window. The retention rules under §10.9 apply to both keys during overlap. | §10.9, §4.3.2 |
|   | 🔐 🛡 | If a clinician's prompt contains PHI, where does that PHI land? The chain is not encrypted. | The chain provides no confidentiality (no IND-CPA per §1.3). When the chain operates over PHI-adjacent flows, §10.22 redaction MUST occur pre-MAC at the SDK; `audit.phi.disposition` records the disposition (`redacted_at_sdk` \| `tokenized_via_vault` \| `excluded_from_capture` \| `no_phi_handling`). A `no_phi_handling` declaration is itself control evidence under HIPAA minimum-necessary. | §10.22, §10.73 HIPAA composition |
|   | 🛠 📋 | What if a small institution claims FIPS 140-2 Level 3 is unreachable? | §10.5 names managed cloud HSMs (AWS CloudHSM, Azure Managed HSM, Google Cloud HSM) as Level-3 conformant at price points reachable by community institutions. The §4 cryptographic floor (HMAC chain + daily Merkle + HSM signature) does not relax for size; the proportionality boundary is at the §10.x extension surface. | §10.5, §1.1 proportionality |
|   | 🛠 | What is the SDK's contract when the local-persistence sidecar fsync fails? | The MAC must be persisted (fsync-local AND/OR ACK-from-ledger) before the entry's payload_hash is disclosed to the next entry. The institution's CC8.1 names the chosen mode and the audit-file header stamps it so the verifier knows which posture produced the chain. | §4.1, §10.25 |

## Audit committee and board governance

| ⭐ | Audience | Question | Answer | Spec |
|---|---|---|---|---|
| ⭐ | 🏛 | What does the chain prove? | It proves that AI decisions captured in production reach the auditor and the examiner in the same form they were made. Nothing was edited in transit; nothing was added retroactively; nothing was dropped from the record. The verifier output is a pass/fail signal an audit committee can rely on without becoming cryptographers. | §1.2, §7 |
| ⭐ | 🏛 📐 ⚖ | What doesn't the chain prove? | It doesn't prove a decision was correct, fair, or compliant with policy. Model risk management (whether a model is sound) and policy compliance (whether the decision met institutional rules) are separate workstreams. The chain is the integrity foundation, not the truth foundation. | §1.2 epistemic scope |
|   | 🏛 📐 | What's the residual risk after we deploy? | Three buckets. (1) Process around the chain — capturing the right events at the right places. (2) SDK-host compromise — decisions corrupted forward in time until detection. (3) Governance changes (key rotations, algorithm changes) that an institution might mismanage. The chain reduces auditability risk; it does not eliminate operational, governance, or model risk. | §1.2, §10.x operational |
|   | 🏛 🛠 | What does this cost to deploy? | SDK integration into capture surfaces is one-time engineering cost. HSM custody for the signing key is ~$20-50K/year at standard cloud-HSM rates. Verifier operation by audit and examination teams is negligible — one binary, no recurring infrastructure. | `docs/cost-model.md` |
|   | 🏛 | How does adoption affect the audit committee's reporting cadence? | The chain produces verifier output any time the audit committee asks for it. Standing reports continue unchanged; chain verification becomes an additional optional input. A committee that wants quarterly verification adds the verifier run to the institution's quarterly cycle. | §7, §10.12 |
|   | 🏛 🛡 | Does the chain support our SOX 404 ICFR opinion? | Conditionally. The chain is admissible for what it proves: integrity of captured events, custody of the signing key, soundness of the daily seal. It is NOT admissible as evidence that a model's decision was correct — model validation is a separate workflow. | §1.1 Daubert, §1.2 |
|   | 🏛 ⚖ | What does becoming a chain operator mean for discovery? | The chain is a permanent, hash-verifiable record of every AI decision. Redaction is pre-MAC at SDK only (§10.22); privilege claims must be pre-tagged (§10.70); litigation-hold and SAR exclusions are categorical, not entry-level. The GC reads one paragraph and understands the discoverability surface. | §1.2.1, §10.13, §10.22, §10.70 |

## Multi-region and multi-tenant operations

| ⭐ | Audience | Question | Answer | Spec |
|---|---|---|---|---|
| ⭐ | 🔍 📋 🛠 | What about multi-region deployment? | Two conformant patterns. **Pattern A** — active-active with seal-region pinning — one canonical `tenant_id` across regions, replicated to a designated seal region, one HSM-signed Merkle root per tenant-day. **Pattern B** — per-region `tenant_id` — one tenant per region with its own IKM, seals, and verifier runs. Run-locality (a run starts and ends in one region) is normative. | §10.15 |
|   | 🛠 📋 | How do we handle a multi-tenant deployment? | Per-tenant IKM, per-tenant chain, per-tenant seal. The envelope carries `tenant_id` as a normative attribute; the verifier walks one tenant at a time. All tenants MAY run under one HSM as long as signing-key access is segregated per-tenant. | §4.4, §3 |
|   | 🏛 🛠 | What about smaller institutions for which HSM cost is meaningful? | Configurable seal cadence (weekly is defensible with examiner approval per §4.2.1) and shared-cloud-HSM deployment shapes scale the spec down. Community institutions adopt §4 + §7 + §10.1–§10.10 and are conformant. | §4.2.1, §1.1 proportionality, `docs/cost-model.md` |
|   | 🔍 🛠 | What's the cross-region run-locality contract under Pattern A when the SDK process is multi-tenant but each tenant has its own region? | One SDK process MUST serve events from exactly one region per Pattern A enforcement. Per-tenant region pinning within one process serving multiple tenants in the same region is institution-side discipline; the CC8.1 names the per-process tenant scope. | §4.4 SDK per-process region binding, §10.15 |
|   | 🛠 📋 | What is the recommended chain posture for a Foreign Banking Organization (FBO) operating a US branch under Reg K? | The US-branch chain MUST be verifiable from US-resident artifacts (verifier binary, IKM custody, HSM cluster) without dependence on home-country systems. Cross-border data transfers under §4.4.1 record the lawful basis at the moment of crossing. | §10.15, §4.4.1, federal-reserve overlay |
|   | 🔍 📋 | What stops the institution from segregating its US chain from holding-company-wide chain so the FRB cannot see consolidated activity? | The chain-coverage map (§10.19) MUST name every legal-entity tenant under the consolidated supervision perimeter. Consolidated supervisors read the full set; gaps are control failures surfaced through the coverage-map disclosure. | §10.19, §10.24 entity succession |

## Examination procedure and findings

| ⭐ | Audience | Question | Answer | Spec |
|---|---|---|---|---|
| ⭐ | 🔍 | What artifacts do we expect to see at exam time? | Three: the ledger (the daily-sealed Merkle tree plus the per-day signed root), the institution's signed public key (with chain-of-custody back to HSM provisioning), and the captured event corpus for the examination period. The §7 verification procedure names every input. | §7 |
|   | 🔍 📋 | What happens if the application process is compromised? | The compromise corrupts events going forward — the attacker can alter what gets captured. It cannot forge events into the past; past events were already chained and exported. The compromise window is bounded by compromise-to-detection latency. | §1.2 fourth-class compromise |
|   | 🔍 📋 🛡 | What's the institution's posture if a chain finding lands? | Findings have normative severity classification. A broken seal under signature is high-severity regardless of cause. A delayed seal with documented explanation and proactive re-attempt is lower severity. The institution does not get to argue down a high-severity finding. | §10.16 severity classification |
|   | 🔍 | What FFIEC IT Handbook coverage does the chain address? | The IT Handbook requires audit logs to be tamper-evident, integrity-protected, immutable, and complete. The AIO booklet §VII.D names AI-decision risks without supplying an audit-trail procedure. The chain closes that procedural gap with named primitives, falsifiable conformance criteria, and a public verifier. | §1, §1.1 regulator-facing alignment |
|   | 🔍 | How do I run the verifier and read the result on my examiner laptop? | §7's three-line `Status:` / `Step:` / `Reason:` form plus §10.12 exit codes (0/1/2/3) plus §10.26 reference-verifier distribution (Cosign-signed, reproducible build, peer-platform binaries). The institution publishes the artifacts; the examiner runs the verifier locally. | §7, §10.12, §10.26 |
|   | 🔍 📋 | Where does the spec name MUST-emit operational events I can sample under MOET? | §10.2 lists 12 operational-event families with MUST-emit semantics. The canonical schema lives in `docs/soc-pack/control-evidence-events.md`; the institution's CC8.1 cross-references the spec section per §10.18. | §10.2, §10.18 |
|   | 🔍 ⚖ | When verifier output says `Status: PASS` with `late-binding entries: N`, what threshold escalates to MRA/finding? | Late-binding is normal-operations behavior (§4.2.2), not integrity violation. The examiner uses judgment; a late-binding ratio > 2% over rolling 30 days is a Significant-deficiency conversation. §4.3.1 names the 36-hour cyber-incident notification rule separately. | §4.2.2, §4.3.1 |
|   | 🔍 📋 | How does an examiner request cadence relaxation (daily → weekly)? | §4.2.1 names written examiner approval. The approval document names the institution, current cadence, requested cadence, justification, sunset date, examiner signature. The chain stamps a cadence-change operational event under §10.2 when the relaxation takes effect. | §4.2.1, §10.2 |
|   | 🔍 ⚖ | Resolution-planning: can the FDIC obtain a forensically complete chain when an institution enters receivership? | §10.24 entity-succession covers M&A / divestiture / receivership; the IKM custodian transfers custody to the FDIC-named successor under documented dual-control, and the chain-coverage map (§10.19) is deliverable to the receiver within the institution's resolution-plan timeline. | §10.24, §10.19, §10.9 retention |
|   | 🔍 ⚖ | Can I cite the chain in an NCUA Document of Resolution, a state-banking consent order, or an NYDFS consent order? | Yes — §10.13 evidentiary artifacts are jurisdictionally portable. The same artifact list grounds DOR, Supervisory Letters, MRA/MRIA, SEC enforcement, state consent orders, and NYDFS consent orders. The institution's CC8.1 names the citation template per regulator. | §10.13, agency overlays |

## Implementation and operations

| ⭐ | Audience | Question | Answer | Spec |
|---|---|---|---|---|
| ⭐ | 🛠 | Where do we put the SDK in our stack? | At every capture point where AI decisions enter operational pathways: the model serving endpoint, the customer-facing surface that consumes the model's output, the overrider's tooling if humans can override model output, and any reviewer interface. | `docs/design/00-overview.md` |
|   | 🛠 | What's the operational burden on SRE/DevOps? | Modest. SDK is in-process; capture is synchronous on the decision path; sealing is a scheduled job (typically daily) that pulls events into a Merkle tree and asks the HSM for one signature. SRE owns seal-job reliability, HSM availability, and ledger durability. | §10.5–§10.10 |
|   | 🛠 | How do we test conformance? | Run `spec/test-vectors/` against your implementation. Positive vectors must verify cleanly; negative vectors must produce documented error codes. The reference implementation is one passing-by-construction baseline; your implementation can differ as long as byte-identical output for the same input. | §7, `spec/test-vectors/` |
|   | 🛠 | What's the SDK's threading model? | Capture is synchronous on the calling thread; per-event MAC computed in-line. Seal job is asynchronous and isolated. Per-process intra-thread concurrency uses stdlib mutexes (`threading.Lock` / `asyncio.Lock` / `Monitor` / `SemaphoreSlim`); `(tenant_id, run_id)` is the single-writer scope. | §10.25, §4.1 |
|   | 🛠 | How do we handle the SDK in a serverless / FaaS environment? | Two models. (1) In-process per invocation, emit per-event MAC, aggregate downstream. (2) Function emits raw events to a streaming sink running the SDK out-of-process before events land in the ledger. The spec is topology-agnostic. | §4, §10.25 |
|   | 🛡 | What's our role when a chain control change is proposed? | Changes (algorithm rotation, key rotation, seal cadence change, IKM custody change) flow through the institution's change-management process. Internal audit reads the change request, verifies spec-compliance, and validates the post-change verifier output. | §10.21 change-management hooks |
|   | 🛠 | What is the back-pressure contract when the ledger is unreachable and the SDK's in-process buffer fills? | The SDK MUST refuse-to-emit when the buffer saturates rather than drop entries silently. The optional `audit.sdk.buffer_saturation_observed` event records the condition; alerting threshold is institution-side per CC8.1. The §10.25 refuse-to-emit posture extends to buffer-overflow. | §10.25, `docs/operator-guide.md` |
|   | 🛠 📋 | What is the normative throughput / latency budget for the SDK's MAC-compute path? | Per-event MAC compute is one HMAC-SHA-256 over ≤ a few KB plus one fsync (Model A) or one HSM round-trip (Model B). Typical 64-bit hosts achieve > 100k events/sec/core for in-memory MAC compute. HSM throughput governs seal cadence per §10.27. | §10.27 |
|   | 🛠 | What is the RTO / RPO contract for the chain in DR? | RPO targets by failure class: HSM unavailability (per §4.3.1 — 36h FFIEC notification clock; per §10.16 mirror-lag posture); ledger unavailability (institution-side RTO per CC8.1); seal-region failover (§10.15 invariant 6 procedure, institution-side RTO). | §4.3.1, §10.15, §10.16 |
|   | 🛠 | What does the SDK do during a leap-second / NTP step-back where `captured_at` goes backwards? | The chain's integrity ordering uses `(run_id, seq)`, not wall-clock timestamps. Backwards `captured_at` within the §4.2.2 clock-skew threshold is an anomaly, not a FAIL.
